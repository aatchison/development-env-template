# Overlays

Overlays are optional capabilities that the baseline `devcontainer.json` can't always carry — either because they require privileged containers, a specific host filesystem, or other launcher-specific permissions.

An overlay is a full, self-contained `devcontainer.json` sitting next to `*.delta.json` inputs. Launchers accept it as a drop-in replacement for the baseline, not as a layer on top of it.

## Available overlays

### `with-claude-mount`

Bind-mounts your host's `~/.claude` into the container at `/home/vscode/.claude`. Your local Claude credentials, history, and settings carry in — no re-login needed.

**Works on:** local Docker (VS Code, devpod-Docker).
**Does not work on:** Codespaces (no host fs), devpod-Kubernetes (no host fs).

### `with-docker-in-docker`

Adds the `docker-in-docker` feature so `docker` commands work inside the container. Requires the container to run privileged.

**Works on:** local Docker (VS Code, devpod-Docker).
**May work on:** devpod-Kubernetes — depends on cluster PodSecurity/admission policy.
**Does not work on:** Codespaces.

## Using an overlay

The devcontainer CLI has two flags that look similar:

| Flag | Semantics | Accepts non-standard filenames? |
|---|---|---|
| `--config` | Load as the config | ❌ rejects anything other than `devcontainer.json` / `.devcontainer.json` |
| `--override-config` | **Replace** the resolved config | ✅ |

Overlays use `--override-config` because (a) their filenames aren't `devcontainer.json`, and (b) they are pre-merged full configs, so "replace" is the correct semantics.

```bash
devcontainer up --workspace-folder . \
  --override-config .devcontainer/overlays/with-claude-mount.json
```

devpod has its own flag name for the same concept:

```bash
devpod up . --devcontainer-path .devcontainer/overlays/with-claude-mount.json
```

VS Code users: open the Command Palette → **Dev Containers: Reopen in Container Using Config File…** and select the overlay.

## How overlays are generated

`*.delta.json` is what you hand-edit. The matching `*.json` is generated by merging baseline + delta.

```
.devcontainer/
  devcontainer.json                        # baseline
  overlays/
    with-claude-mount.delta.json           # INPUT — you edit this
    with-claude-mount.json                 # OUTPUT — generated, do not edit
    with-docker-in-docker.delta.json       # INPUT
    with-docker-in-docker.json             # OUTPUT
```

Regenerate after editing a delta or the baseline:

```bash
./scripts/build-overlays.sh
```

The generator uses `jq -S -s '.[0] * .[1]'` — deep-merges objects, **replaces arrays**. More on that below.

## Drift check

CI runs `./scripts/check-overlay-drift.sh`, which regenerates overlays into a temp directory and diffs them against the committed copies. If they differ, CI fails and tells you to re-run the generator.

Run the check locally before pushing:

```bash
./scripts/check-overlay-drift.sh
```

## Gotcha: jq `*` replaces arrays

The merge operator `*` in jq deep-merges **objects** but **replaces arrays**. This matters when the baseline and a delta both define the same array key.

Example — if baseline has:

```json
{ "mounts": ["source=foo,target=/foo,type=bind"] }
```

…and a delta has:

```json
{ "mounts": ["source=bar,target=/bar,type=bind"] }
```

…the merged result drops the baseline entry:

```json
{ "mounts": ["source=bar,target=/bar,type=bind"] }
```

**Workaround:** if you need to union arrays, the delta must include the baseline entries too, or switch to an object-valued key. For `features`, this isn't an issue — `features` is an object, not an array, so deltas can add features without wiping baseline ones.

## Adding a new overlay

1. Create `.devcontainer/overlays/<name>.delta.json` with only the fields that should override or extend the baseline. Keep it minimal.

   Example — adding a port forward:
   ```json
   {
     "forwardPorts": [8080]
   }
   ```

2. Regenerate:
   ```bash
   ./scripts/build-overlays.sh
   ```

3. Verify the generated `<name>.json` looks right. Commit both the delta and the generated file.

4. Update the README's environment matrix and `docs/launchers.md` if the overlay has launcher-specific support.

## Why not just layer overlays at runtime?

The devcontainer spec doesn't have a first-class "layer on top" mechanism for config files. `--override-config` is replace-semantics, not merge-semantics. Pre-merging with jq gives us:

- A single file launchers can consume with no special flags beyond `--override-config`.
- CI that can diff generated output against what's committed — drift is visible.
- No runtime surprises from order-of-application.

The tradeoff is discipline: never hand-edit generated `.json` overlays. CI will catch it, but it's still churn.
